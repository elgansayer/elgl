# Chat photo and video sharing

Issue: #1170

## Product contract

Chat rooms support direct photo and video sharing from the composer. The picker shows a preview and an explicit **HD quality** toggle before upload.

Supported source formats:

- images: JPEG, PNG, WebP;
- videos: MP4, WebM, QuickTime/MOV.

Quality envelopes are intentionally bounded:

| Media | Standard | HD |
| --- | ---: | ---: |
| Image | 6 MiB after client preparation | 15 MiB after client preparation |
| Video | 12 MiB source | 25 MiB source |

Standard images are prepared at up to 1600×1600 with JPEG quality 0.78. HD images are prepared at up to 2560×2560 with JPEG quality 0.90. Browser video transcoding is deliberately not attempted because codec availability, audio preservation, thermal cost and browser support are inconsistent; Standard therefore accepts source video inside the smaller envelope while HD preserves a larger source file. A later durable media pipeline may add server-side derivatives without changing this UI contract.

## Upload and send flow

1. The authenticated Angular client asks `POST /media/chat/presigned-url` for an upload intent containing filename, declared content type, selected quality and byte count.
2. Nest validates the request, applies the purpose-specific MIME/size policy and creates a server-owned object key under `chat-media/<user>/<image|video>/<standard|hd>/...`.
3. Nest returns a short-lived signed Cloudflare R2 gateway PUT URL. No Cloudflare credential is exposed to the browser.
4. The browser uploads bytes directly to the R2 gateway.
5. After the PUT succeeds, Angular calls `POST /media/chat/send` with only the room ID, media kind and server-issued object key.
6. The backend rechecks that the object key is owned by the authenticated user, derives the public compatibility URL server-side and passes the message through the existing `ChatService`, preserving room/safety/filter checks and Centrifugo publication.
7. Chat renders images lazily and videos with native controls and metadata-only preload.

The generic `POST /chat/messages` DTO intentionally continues to reject `image` and `video` types. This prevents clients from bypassing the media boundary with arbitrary external URLs or another user's R2 object.

## Retry and concurrency behavior

An uploaded object is a stable retry key. `POST /media/chat/send` first looks for an existing message from the same sender using that media URL. The partial unique index on `(sender_id, media_url)` for image/video messages provides the database backstop for concurrent retries.

This matters because the existing chat pipeline persists a message before publishing it to Centrifugo. If publication or the HTTP response fails after persistence, the next retry returns the already-persisted row instead of creating a duplicate.

If the upload succeeds but message delivery fails, the composer keeps the uploaded object in memory and exposes **Retry send**. Retrying does not upload the bytes again. **Dismiss** forgets the client retry state; it does not delete an object whose send outcome may be ambiguous.

## Security and privacy

- Both presign and send endpoints require `SupabaseAuthGuard`.
- Presign is throttled to 30 requests/minute per configured throttler policy; send is throttled to 60 requests/minute.
- Object keys are generated by Nest using a CSPRNG nonce and are scoped to the authenticated user, media kind and selected quality.
- The server ignores the source filename when choosing the R2 object key.
- Filename and content-type metadata are bounded before processing.
- SVG, HTML and executable-like formats are not accepted by the chat media intent.
- The R2 gateway enforces the signed method, exact key, content type and byte ceiling during transfer.
- The send boundary derives the URL from the owned object key; the browser cannot choose the published media URL.
- Rendering accepts HTTP(S) media URLs only and does not inject user HTML.
- Application logs must not contain media bytes, signed upload URLs, authorization tokens or message content.

The repository's Cloudflare-native media architecture currently exposes compatibility public URLs for existing product contracts. Durable private asset records, byte verification, derivatives and authenticated delivery are tracked by the shared media-finalisation work documented in `docs/cloudflare-native-media.md`; this feature does not introduce an alternate AWS/S3 path.

## Accessibility and responsive behavior

- The media action, cancel, upload, retry and dismiss controls retain touch-sized targets.
- The composer action row wraps at narrow widths and high browser zoom rather than clipping the new control.
- The picker uses a labelled native file control and a labelled HD checkbox.
- Upload and send failures use `role="alert"`; retry state remains keyboard reachable.
- Image previews and received images have text alternatives; received video uses native keyboard-accessible controls.
- The dialog is modal-labelled and the controls do not rely on color alone to communicate quality or failure.

## Failure behavior

| Failure | User-visible behavior | Data behavior |
| --- | --- | --- |
| Unsupported type | Selection/upload is rejected | No presign or object |
| Oversized prepared file | Upload is rejected with the selected quality limit | No presign or object |
| Authentication missing | Operation fails closed | No presign/send |
| R2 PUT fails | Picker stays available with an error | No chat message |
| Chat send fails before persistence | Retry send remains available | Same object key is reused |
| Response/Centrifugo fails after persistence | Retry resolves the existing message | No duplicate message |
| Delivery-state database lookup fails | Send fails closed | No unverified retry is attempted |
| Object already used in another room/type | Send returns conflict | Existing message is preserved |

The upload object can outlive a dismissed or abandoned picker. R2 lifecycle/reconciliation remains part of the repository-wide media finalisation policy; do not guess that an ambiguous send failed and delete media that may already back a persisted message.

## Deployment

1. Deploy the R2 gateway configuration already required by the Cloudflare-native media stack.
2. Apply the Supabase migration so retry uniqueness exists before clients can send media.
3. Deploy the backend presign/send endpoints.
4. Smoke-test Standard and HD image uploads, Standard and HD video uploads, a deliberately oversized source, a send retry after a simulated response failure, and another user's object key.
5. Deploy the Angular composer and renderer.
6. Monitor presign rejection rate, R2 upload failures, media-send conflicts and chat publication failures without logging URLs containing upload signatures or user media.

## Rollback

Rollback the Angular media composer first so no new upload intents are created, then roll back the backend feature. The partial unique index is safe to leave in place because it only constrains `image`/`video` rows to one message per sender/object. If it must be removed after application rollback:

```sql
DROP INDEX IF EXISTS public.chat_messages_sender_media_url_unique_idx;
```

Do not roll back by reopening arbitrary media URLs on the generic chat-message endpoint, exposing R2 credentials, or bypassing ownership checks.
