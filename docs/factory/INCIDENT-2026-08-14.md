# OpenHands Factory incident: 2026-08-14 → 2026-08-15

## TL;DR

The factory daemon (`hellotalk-factory.service`, on the production host) had
merged nothing autonomously for ~23 hours when this investigation started
(last real merge: a dependabot PR at 2026-08-13 21:17 UTC). The user's report
started as "no PRs merged, no PRs fixed, no tickets worked on" and "many
failures to Telegram." Investigation found **not one bug but a chain of
17 distinct, independently-blocking bugs**, fixed one at a time, each
verified live on the host before moving to the next - two of them
(#17, #18) not factory bugs at all, but real application bugs discovered
only because they were blocking every factory verification run. As of this
writing the daemon has all 17 fixes deployed and the backlog has been reset
to retry immediately; no autonomous merge had landed yet at time of writing,
but per-job error rates dropped sharply after each fix and jobs are reaching
states (`verifying`, `reviewing`, real acceptance-criteria rejections, real
Cypress e2e runs) that were previously unreachable. See "Current status"
below for the live picture at handoff time - it will already be stale by the
time you read it, so re-verify rather than trust it.

**If you are picking this up cold**: read "How to resume investigating"
first. Do not assume the next failure is infra - several of today's hours
were spent confirming that a failure was genuinely a legitimate code-quality
rejection (real ESLint warnings, real failing tests, a real acceptance
criterion not met) rather than another infra bug. The system is *supposed*
to reject bad PRs; that is success, not failure.

## Why this took so long: the actual failure chain

Each fix below unblocked the *next* failure, which had been completely
invisible until the one before it stopped firing constantly. This is why the
user kept seeing "still 0 movement" after each individual fix - only after
several links in the chain were fixed simultaneously could the queue's
overall behavior actually change. Read them in order; the numbering matches
the order they were found and fixed.

### 1. Rootless Podman cgroup delegation (PR #3549)

**Symptom**: worker containers intermittently failed to start at all, with
`runc create failed: unable to apply cgroup configuration ... permission
denied` on `mkdir /sys/fs/cgroup/system.slice/<hash>`.

**Root cause**: the `hellotalk-factory` service user had no real systemd
user session, so Podman fell back to a cgroupfs mode that raced and failed
under concurrent container starts.

**Fix**: `loginctl enable-linger hellotalk-factory` (creates
`user@988.service`, persists across reboots) plus
`Environment=XDG_RUNTIME_DIR=/run/user/988` on the systemd unit, so Podman's
`--userns=keep-id` has a real session to delegate cgroups through.

### 2. Disk full (no code fix - live remediation only)

**Symptom**: `unable to write file ...`, `could not lock config file
.git/config: File exists`, and other git errors that looked like corruption.

**Root cause**: `/var/lib/hellotalk-factory` (a separate `/dev/sdb` mount)
was at 100% (56 MB free of 50 GB) from 540 never-cleaned-up stale git
worktrees (30 GB) and 207 crash-recovery backups (12 GB).

**Fix**: cleaned up live (`git worktree remove` for worktrees belonging to
`done`/`quarantined` jobs, `rm -rf` for the recovery directory). No code
changed. Disk is now at ~17-20% used. **This can recur** - nothing currently
automates worktree/recovery cleanup on a schedule; only `refresh()`'s
issue-closed-before-PR path and the review-report clearing (fix #7) clean up
after themselves. Worth adding a periodic sweep if disk pressure returns.

### 3. Stale base repository checkout (no code fix - live remediation only)

**Symptom**: `security-review`/`quality_repair`/`architect` phases failed
with `[Errno 2] No such file or directory:
.../automation/prompts/security.md` (etc.) - files that definitely existed
on `origin/main`.

**Root cause**: `/var/lib/hellotalk-factory/repository` (the base checkout
worktrees are created from) was 296 commits behind `main`
(pinned at a commit from 2026-08-09). `git fetch origin main` was being run
correctly, but nothing ever did a `git reset --hard`/`git pull` on the base
checkout's own working tree - fetch only updates refs, not files. See fix
#11 for the code-level version of this same class of bug, which is now
structurally impossible for prompt files specifically.

**Fix (live)**: `git reset --hard origin/main` on
`/var/lib/hellotalk-factory/repository`. **This can and will recur** unless
something re-syncs it periodically - nothing added to the codebase does this
automatically yet. This was one candidate durable fix considered and
rejected in favor of #11 (reading prompts from the worktree instead, which
is always fresh) because a periodic `git reset --hard` on the *shared* base
repo risks racing concurrent worker threads doing `git fetch`/`git
worktree add`/`git push --set-upstream` against the same `.git` directory
(this exact race is the likely cause of the `could not lock config file
.git/config` error seen on jobs #3548 and others - still unresolved, low
frequency, not chased further tonight).

### 4. Cross-provider LLM tool-call ID replay crash (PR #3554, #3555 config)

**Symptom**: `litellm.BadRequestError: ... Invalid 'input[1].id': '<uuid>'.
Expected an ID that begins with 'fc'.` - killed the whole conversation
outright, no recovery.

**Root cause**: `openhands.sdk`'s `FallbackStrategy` retries the *primary*
model first on every new conversation turn (fallback is per-call, not
per-conversation). A conversation that dipped to a fallback provider on one
turn (Gemini/OpenCode format) and back to the strict-validating primary
(OpenAI's real Responses API) on the next replayed the fallback's
foreign-formatted tool-call ID into the primary, which rejects it outright.
This is an open, unmerged upstream litellm bug:
<https://github.com/BerriAI/litellm/pull/34387> (open since 2026-07-23).

**Fix**: removed per-call cross-provider fallback entirely.
`select_primary_provider()` (`provider_profiles.py`) now picks exactly one
provider tier per conversation, breaker-aware (openai-subscription →
opencode-go → gemini-flash, in that order, matching what the user
confirmed they expect). Resilience across tiers now comes from the job's
own retry-with-backoff picking a fresh, healthy tier each attempt, not
from a fallback chain inside one conversation.

### 5. Missing `.git` mount in the worker sandbox (PR #3550)

**Symptom**: `reviewed_sha: 0000000000000000000000000000000000000000` in
review reports (an all-zero placeholder SHA), and generally *any* git
command the agent ran itself (inside its sandboxed terminal) failed with
`fatal: not a git repository`.

**Root cause**: a git worktree's `.git` is a *file* pointing at an absolute
host path under the shared base checkout
(`repository/.git/worktrees/<name>`) - that's where git keeps the real
git-dir for a worktree, not inside the worktree itself. The sandboxed
container only ever mounted the worktree directory; it never had access to
that path, so every git command failed.

**Fix**: mount `{repository}/.git` read-only at the same absolute path
inside the container. Read-only is safe/correct: the daemon (outside the
container) owns every actual git mutation (add/commit/push); the sandbox
never needs write access to the object database.

### 6. Container ran as the wrong uid (part of PR #3550)

**Symptom**: even after fix #5, `.git` access still failed - now with
`Permission denied`, not `fatal: not a git repository`.

**Root cause**: the worker image's default user (`worker`) is an arbitrary
numeric uid (1000) baked into the image, unrelated to the host. Podman's
`--userns=keep-id` only maps uid *numbers* between host and container - it
does not change which uid the container's process actually runs as. Since
the daemon creates all worktree/git metadata with a restrictive `0600`/
`0700` umask (`UMask=0077` in the systemd unit), none of it was readable by
`worker`, even from inside the already-working primary workspace mount.

**Fix**: added `--user={daemon's own uid}:{gid}` (988:988 on this host) to
every podman invocation.

### 7. Podman's own runtime-config lookup intermittently fails (PR #3551)

**Symptom**: `Failed to obtain podman configuration: lstat
/run/user/988: permission denied` - a pre-existing, host-level flakiness,
confirmed to predate *any* fix made in this session (423 occurrences going
back to 08:00 UTC on 2026-08-14, well before the linger fix in #1 was even
applied). Had **no retry path at all** - neither `resource_limit_error()`
nor `namespace_error()` matched this error text, so every hit failed the
terminal command outright with zero recovery.

**Fix**: added `podman_configuration_error()` matching this text, routed
through the existing cgroup/namespace fallback path (which already avoids
the systemd session via `cgroup_manager=cgroupfs`/`userns=host`), and - key
change - the retry now drops `XDG_RUNTIME_DIR` from its environment instead
of pointing the retry at the same flaky lookup again. Verified via repeated
manual runs that dropping the variable resolves it reliably. Root cause of
the underlying flakiness itself (why the lookup fails sometimes) was **not**
fully diagnosed - only worked around with a reliable retry path. Worth
revisiting if it recurs at high frequency.

### 8. Review conversations re-validated stale, hours-old reports (PR #3552)

**Symptom**: `Structured review report SHA 0000...0000 does not match
expected head <sha>` - persisting on jobs that had *just* been retried,
well after fix #5/#6 were deployed and confirmed working elsewhere.

**Root cause**: `worktree` persists across retries of the `REVIEWING`
state. `.factory-review.json` was never cleared between attempts. If a
conversation crashed or ran out of its turn budget before rewriting it, the
*next* attempt's `validate_review_report()` silently re-validated the
*previous* attempt's stale file - in one traced case, a file over an hour
old, timestamped before the fix that would have let the agent write a
correct one.

**Fix**: delete `.factory-review.json` before running the review
conversation each time, so a conversation that fails to (re)write a valid
report is now correctly reported as "missing" for *that* attempt, not
judged against unrelated stale output.

### 9. Requiring the model to self-report `reviewed_sha` (PR #3553)

**Symptom**: `Structured review report missing valid 'reviewed_sha'` on
otherwise-excellent, fresh, genuinely thorough reviews (confirmed live on
PR #3527: a detailed, well-evidenced, correct rejection that simply omitted
one JSON field).

**Root cause**: the model was never actually the trustworthy source for
this value - the orchestrator already captures the correct commit via
`workflow.head_sha()` on the host, before the conversation even starts, and
nothing else touches the worktree concurrently during one job attempt.
Requiring the model to also report it back and cross-checking the two added
a frequent, needless failure point (a forgotten field or placeholder value
failed an otherwise-valid review) with no real integrity benefit - the
comparison in `pipeline.py`'s `REVIEWING` handler was already comparing two
host-computed values that were structurally always equal.

**Fix**: dropped `reviewed_sha` entirely - from the schema in
`review.md`, from `validate_review_report()`'s parameters/checks, and the
now-vacuous comparison in `pipeline.py`.

### 10. DeepSeek "thinking mode" `reasoning_content` bug (PR #3554)

**Symptom**: `litellm.BadRequestError: ... Error from provider (Console
Go): ... The reasoning_content in the thinking mode must be passed back to
the API.` - killed the whole conversation.

**Root cause**: a well-documented, still-open litellm bug class specific to
DeepSeek V4's thinking mode - `reasoning_content` emitted on one turn isn't
correctly forwarded on the next multi-turn request. See e.g.
<https://github.com/BerriAI/litellm/issues/26395> and
<https://github.com/BerriAI/litellm/pull/28080> (both DeepSeek V4, both
still open/reopened upstream, as of 2026-08-14).

**Fix**: `reasoning_effort="none"` on the opencode-go (`deepseek-v4-flash`)
LLM instance, disabling thinking mode for that tier entirely. Scoped to
that one tier only - openai-subscription and gemini haven't shown this
failure mode.

### 11. Provider usage-limit resets ignored (PR #3555)

**Symptom**: `litellm.RateLimitError: ... "The usage limit has been
reached", "resets_at": ..., "resets_in_seconds": 496742` (~5.75 *days*) -
and the job kept retrying that tier every ~5 minutes regardless, burning a
full conversation attempt each time on a tier that could not possibly
succeed for days.

**Root cause**: `classify_failure()` didn't match `"usage limit"` as
anything (fell through to generic `TRANSIENT`), and even a correctly
classified `RATE_LIMIT` only opened the circuit breaker for the fixed
`FACTORY_PROVIDER_COOLDOWN_SECONDS` (300s), ignoring how long the provider
itself said the outage would actually last.

**Fix**: `classify_failure()` now matches `"usage limit"` too.
`extract_retry_after_seconds()` reads the embedded `"resets_in_seconds"`
value out of the error body. `CircuitBreaker.record_failure()` accepts an
optional `retry_after_seconds` and, when longer than the configured
cooldown, keeps the breaker open for that long instead (capped at 7 days so
a malformed/absurd value can't wedge a provider open indefinitely;
`record_success()` clears the override so it never outlives the failure
that set it).

### 12. Untracked files invisible to the verification diff (PR #3558)

**Symptom**: `No changed paths were found` in the `VERIFYING` state, right
after the *same* job had just passed the `IMPLEMENTING` phase's
`has_changes()` check.

**Root cause**: `has_changes()` (`git status --porcelain`) counts a new
*untracked* file as a change; `changed_paths()` (`git diff --name-only
<ref>`) never reports untracked files at all - `git diff` only compares
tracked content. A task whose only output was a new file (not an edit to an
existing one) passed the first gate, burned a full security-review cycle,
and only then failed verification with a confusing error - instead of
being judged, correctly, on the file it actually added. Reproduced live:
issue #693's worktree held nothing but an untracked file the agent left
behind (a permission-debugging probe, itself a symptom of environment
issues from earlier in the incident) and failed exactly this way.

**Fix**: `changed_paths()` now merges in `git ls-files --others
--exclude-standard` so both checks agree on what counts as "changed."

### 13. Orphaned verification server processes (also PR #3558)

**Symptom**: `curl: (7) Failed to connect to 127.0.0.1 port 4200` on the
`frontend-e2e` verification step, and a live-caught casualty: an `ng
serve` process that had been running for 5h47m, reparented to init, still
consuming memory.

**Root cause**: `run_process()` used `subprocess.run(timeout=...)`. On
timeout, that only kills the *immediate* child (`bash`) - `SIGKILL` can
never be trapped, so `bash`'s own `trap ... EXIT` cleanup for anything it
backgrounded (the e2e step's `npm start &` dev server) never runs, and the
backgrounded process is orphaned instead of terminated.

**Fix**: rewrote `run_process()` around `subprocess.Popen` with
`start_new_session=True` and an explicit `os.killpg()` in a `finally`
block, so the whole command tree is reliably terminated regardless of how
it exits - normal completion, timeout, or anything else.

### 14. Frontend e2e startup wasn't resilient (PR #3559)

**Symptom**: same port-4200 connection failures as #13, even after that
fix - because a 60-second budget for a cold Angular compile under load is
genuinely tight on its own, and if `npm start` crashed immediately the
script still burned the full 60s polling a dead server with zero
diagnostic output.

**Fix**: extended the wait to 180s; polls the server *process* itself each
iteration and fails immediately (with the server's own log tail) if it has
already exited, instead of waiting out the remainder of the budget against
a server that was never coming back; on a genuine timeout, also surfaces
the log tail.

### 15. `PORT=3000` environment leak (live config fix - no PR, not in git)

**Symptom**: *the actual root cause of nearly all of #13/#14's underlying
port-4200 failures*, discovered only after fixing the zombie-process and
timeout-hardening layers on top of it. A dev-server log dump (surfaced by
fix #14's new diagnostics) showed the Angular dev server had started fine
- on port **3000**, not 4200.

**Root cause**: `/etc/hellotalk-factory/factory.env` (the systemd unit's
`EnvironmentFile`, not tracked in git) had a stray `PORT=3000` line,
inherited by every subprocess the daemon spawns. Angular's newer
Vite-based dev-server (`@angular/build:dev-server`) respects `PORT` as an
override. `backend/src/main.ts` already defaults to 3000 on its own
(`process.env.PORT ?? 3000`) - so this variable was a complete no-op for
the backend and *purely harmful* for the frontend, silently redirecting
every e2e verification's dev server to the wrong port, for as long as that
line had been in the file (unknown - not tracked, not documented anywhere,
not in `config/systemd/factory.env.example`).

**Fix**: removed the line from the live file, restarted the daemon.
**This is not in git** - if the host is ever reprovisioned from
`factory.env.example`, this specific line won't reappear (it was never
there), but if anyone manually re-adds a bare `PORT=` to `factory.env` for
an unrelated reason, this will recur silently. Consider either
documenting *why* it must not be set, or having the frontend-e2e
verification command explicitly `unset PORT` before invoking `npm start`
so this class of leak can't recur regardless of what's in the daemon's own
environment.

### 16. Workspace mounted at a generic `/workspace` alias, not its real path (PR #3567)

**Symptom**: `Structured review report missing` (not "invalid" - genuinely
absent) recurring on *fresh* retries, well after fixes #5/#6/#8/#9. Found
by reading an actual live conversation transcript end to end (not
inferring from `last_error` text) for job #3557: the agent successfully
wrote `.factory-review.json` via the `file_editor` tool, then tried to
confirm it via `ls`/`cat` from the *terminal* tool using the exact same
path `file_editor` had reported - and got `No such file or directory`. It
then spent the rest of its conversation turn budget debugging a
permissions problem that did not exist, and the conversation ended without
ever finishing a valid report.

**Root cause**: `ContainedFileEditorExecutor` (the `file_editor` tool)
edits the filesystem directly and reports/accepts real host paths
(`/var/lib/hellotalk-factory/worktrees/issue-N/...`) - it doesn't run
through the sandboxed container at all, since it's a trusted,
already-confined SDK component with no code-execution risk. But the
*terminal* tool's container mounted that same directory at a generic
`/workspace` alias. A path the agent got back from one tool was never a
path the other tool could resolve, and vice versa. **This is plausibly the
single highest-impact fix of the whole incident**: it would derail
essentially any conversation that cross-references a path between editing
a file and verifying it from the terminal, which is extremely common agent
behavior, and was likely a real contributing factor - not the sole cause,
but a compounding one - behind a meaningful fraction of the `verifying` and
`reviewing` failures attributed to other causes above.

**Fix**: mount the workspace at the identical absolute host path inside
the container (matching the pattern already used for the `.git` mount in
fix #5), instead of a generic `/workspace` alias. Updated `--workdir` and
the `node_modules` read-only bind mounts to match. Verified live: the
container now resolves the worktree at the exact path `file_editor` uses,
and git access still works.

### 17. `frontend/assets/config.json` 404s - an application bug, not a factory bug (PR #3569)

**Symptom**: with every fix above deployed, job #348 got further than any
job had all night - a real, live Cypress e2e run against a real dev
server (fixes #1-#16 all held). Result: **10 of 11 spec files failed, 289
of 326 individual tests failed (91%)** - across every unrelated feature
area (chat, payments, matchmaking, trust & safety, video classrooms,
discovery map...), not just whatever job #348's own change touched.

**Root cause**: read an actual Cypress failure screenshot (not just the
truncated `last_error` text - screenshots live under
`<worktree>/frontend/cypress/screenshots/<spec>.cy.ts/*.png`, readable
after `sudo cp`+`chmod` out of the worktree). It showed: `GET
/assets/config.json` returns 404 → `ConfigurationService` catches it and
logs `"Failed to load configuration. Using fallback."` via
`console.error` → the e2e test harness's global rule treats *any*
`console.error` as an automatic failure (`Error: E2E FAILURE:
console.error was called with: {}`). The file itself was never missing -
`frontend/src/assets/config.json` existed - but the app's build had
already migrated static assets to Angular's newer `public/` directory
convention (`angular.json`'s `assets` glob only copies from `"public"`),
and this one file was left behind in the old location, so it was never
copied into what `ng serve`/`ng build` actually serves. **This bug
predates tonight entirely** - it 404s in production too, not just in
this sandboxed environment; `ConfigurationService`'s graceful fallback is
exactly why nobody noticed a user-facing symptom.

**Fix**: `git mv frontend/src/assets/config.json
frontend/public/assets/config.json`. Verified locally (not just live on
the host): `GET /assets/config.json` returns 200 with the correct
content from `ng serve`, the file is present in `ng build`'s production
output, and `configuration.service.spec.ts`'s existing unit tests pass
unchanged. **This was very plausibly the dominant remaining blocker for
any frontend-touching job reaching a merge** - every one of them was
doomed to fail e2e verification regardless of what was implemented, no
matter how correct, until this was fixed.

### 18. The verification semaphore serialized everything, not just the port-sensitive step (PR #3570)

**Symptom**: not a correctness bug - a throughput one, raised directly by
the user ("do we have too much testing... is it slowing things down").
Any `frontend/`-touching change runs 14 sequential verification commands
(constitution, conflict-markers, factory's own tests, 6 frontend checks,
frontend-e2e, 4 backend checks) - and `verification_slots`
(`Semaphore(1)` in `daemon.py`) wrapped the *entire* list, not just
`frontend-e2e`. With `FACTORY_MAX_PARALLEL_JOBS=3`, that meant only one
worker could ever be verifying anything at a time, even a 10-second lint
check, if another worker happened to be mid-verification already -
effective verification parallelism was 1, not 3.

**Root cause**: the semaphore exists to prevent concurrent
`frontend-e2e` runs from colliding on the fixed port `npm start` binds
(`127.0.0.1:4200`) - a real constraint - but it was applied to the whole
suite instead of just that one command. `backend-test:e2e` looks like it
would have the same problem, but doesn't: confirmed by reading its actual
test setup (`backend/test/*.e2e-spec.ts`) that it uses NestJS's
`createNestApplication()` + `supertest` against `app.getHttpServer()`
in-process, on an ephemeral port assigned per test process, not a fixed
bound port.

**Fix**: added `VerificationCommand.exclusive` (true only for
`frontend-e2e`). `_verify()` (`pipeline.py`) now runs every shared
command with no semaphore, then only the exclusive command(s) through
`verification_slots`. As a side effect, cheap checks now fail fast before
minutes are spent on e2e, regardless of `frontend-e2e`'s position in the
list returned by `commands_for()`.

**Considered and explicitly deferred**: scoping the e2e suite down to
only specs relevant to what changed (rather than always running the full
326-test suite). Real potential speed win, but risks silently skipping a
regression the current blanket approach would have caught, on a system
that merges without human review - not a call to make unilaterally at
4am. Left as an open option, not implemented; see "Known open items."

### 19. PR-review jobs starved by scheduling order (PR #3572)

**Symptom**: user asked directly whether PRs were actually being reviewed
and merged. They weren't, even after fixes #1-#18 landed: 26 open
PR-review jobs sat untouched regardless of how many infra bugs got fixed.

**Root cause**: `select_batch()` (`daemon.py`) sorts eligible jobs by
`(task.priority, int(task.identifier))` ascending. Issue tasks and
PR-review tasks shared the same priority (10), and PR numbers are
consistently *higher* than the issue backlog's identifiers (PRs are
newer), so every PR-review job sorted behind the entire issue backlog -
queue position 27+ no matter what else got fixed.

**Fix**: `collect_open_pull_requests()` (`github.py`) now assigns
priority `5` (between guardian-alert at `0` and ordinary issues at `10`),
so PR review is worked before general issue implementation without
starving guardian-alert work. User picked this over the alternative
(interleaving) when asked directly.

### 20. Worktrees for jobs closed mid-review never got cleaned up (PR #3573)

**Symptom**: `refresh()`'s worktree-cleanup loop only fired for jobs
still in `PRE_PULL_REQUEST_STATES`. A PR-review job left in `REVIEWING`,
`CI_PENDING`, or `MERGE_QUEUED` whose external PR was closed (not
merged) while the factory was still working on it never got cleaned up -
worktree, lease, and disk usage all leaked indefinitely.

**Fix**: broadened the skip condition to `job.state in TERMINAL_STATES`
(`DONE`/`QUARANTINED` only), so cleanup now fires for any non-terminal
state once the underlying task is no longer active - still guarded by
`protected_task_ids`, which the daemon populates from currently-running
workers, so an in-progress job is never touched. Gave PR-driven closures
a distinct `last_error` message from issue-driven ones for clearer job
history.

### 21. Base repository ownership corrupted by out-of-band root commands (live remediation + PR #3574)

**Symptom**: while investigating why ~13 of 23 in-flight PR-review jobs
were all failing with "Structured review report missing" (the review
conversation never wrote `.factory-review.json`), a live `journalctl -f`
tail caught a review conversation getting `Permission denied` on every
single file access inside its own worktree (`ls .`, `cat AGENTS.md`,
`stat AGENTS.md`) - not the already-fixed `/workspace`-alias bug (fix
#16), a new-looking failure using real worktree paths.

**Root cause**: `find /var/lib/hellotalk-factory -not -user
hellotalk-factory` turned up 858 files, all under the shared base
checkout at `.../repository`, owned by `root` instead of the
`hellotalk-factory` daemon user - including `.git/index`,
`.git/refs/heads/main`, and `.git/ORIG_HEAD`. Some out-of-band
root-privileged `git`/`sudo` command (almost certainly manual diagnostic
work earlier this session, run without `-u hellotalk-factory`) had
touched the base repo directly. A `git fetch`/`merge --ff-only` as
`hellotalk-factory` afterward failed silently on writing `.git/index`,
which is consistent with (though not proven to fully explain) the
missing-review-report pattern: worktrees are created from this base via
`git worktree add`, and the daemon's own git plumbing against the shared
`.git` needs write access to files a root-owned index would deny.
Restoring ownership also let the base checkout `git fetch`/fast-forward
cleanly for the first time in a while - it had drifted 16 commits behind
`origin/main`.

**Fix**: `sudo chown -R hellotalk-factory:hellotalk-factory
/var/lib/hellotalk-factory/repository` (live remediation, not a code
change - nothing in the codebase caused this). Separately, found that the
factory's own conversations had previously committed scratch files
(`perm_test*.txt`, `perm_probe_1907.txt`) while probing this exact class
of permission bug themselves, and one such commit slipped through review
and merged to `main` in PR #3377; PR #3574 removes them.

**Not fully closed**: the intermittent nature of the underlying container
`Permission denied` (not reproducible on demand with identical `podman
run` arguments run manually, including under a deliberate 24-container
concurrency stress test - see fix #22) suggests it was not primarily a
podman race after all; fix #22 below is the more likely actual cause.

### 22. No locking around git operations on the shared base git dir (PR #3576)

**Symptom**: after fix #21, fresh (post-restart) retries of several
PR-review jobs *still* failed with "Structured review report missing"
or `SystemExit: 124` (the 120-minute task timeout) - so #21 was real but
not sufficient. A live `journalctl -f` tail caught a review conversation
getting `Permission denied` reading a properly-owned worktree file, with
the agent's own diagnosis inside the transcript: "Git object files are
mode 440 root:root... many objects are unreadable." A 24-container
concurrent stress test against the same read-only `.git` mount could not
reproduce this in isolation, ruling out a simple podman `--userns=keep-id`
race as the primary cause.

**Root cause**: `git_workflow.py` had zero locking or retry around any
git command that mutates the shared base repository's `.git` dir
(`fetch`, `worktree add`, `worktree remove`, `push`) - every task
worktree shares one `.git` dir (`worktrees/`, `objects/`, `config`,
`refs`) in the base repository. With `FACTORY_MAX_PARALLEL_JOBS=3`,
concurrent workers routinely collide on git's own advisory locks against
that shared state - this is very likely what the already-documented,
previously-unfixed `could not lock config file .git/config: File
exists` error (see old "Known open items") was actually telling us, and
plausibly what a container reading `.git` mid-write from a *different*
worker's concurrent git operation was catching as transient/wrong
metadata.

**Fix**: added a bounded retry (`_run_with_lock_retry`, up to 5 attempts
with linear backoff) around the four git-mutating call sites, triggered
only on stderr matching known lock-contention markers. A lock collision
means git never attempted the operation, so retrying is safe - nothing
partially happened that a retry could duplicate or corrupt. A real
failure (bad host, real conflict) still fails immediately, no added
delay.
