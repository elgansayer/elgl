# Global Angular client crash reporting

Issue: #1420

## Runtime contract

Angular registers `GlobalErrorHandler` as the application-wide `ErrorHandler` in `frontend/src/app/app.config.ts`. Unhandled browser errors are normalised and sent on a best-effort basis to `POST /api/analytics/client-error`.

The reporting path must never become a second application failure. The handler therefore catches its own normalisation/reporting failures, does not rethrow unknown throwables, and swallows network failures from the telemetry request. Promise-style wrapper objects are only unwrapped when an own property contains a real `Error`; arbitrary getters or `toString()` implementations are never invoked.

Client reporting is intentionally disabled during SSR. Server-side failures belong in server logs rather than making an HTTP request back into the same application.

## Privacy and security boundary

Crash telemetry is operational diagnostic data, not a general-purpose event payload.

The browser:

- truncates messages, names, stacks, URLs, user agents, metadata strings and stack frames;
- strips query strings and fragments from page/request URLs;
- redacts Bearer credentials, JWT-shaped values, and common token/API-key/password query parameters;
- sends at most 20 parsed stack frames;
- accepts only primitive allow-listed metadata generated by the handler;
- deduplicates identical crashes for 10 seconds;
- emits at most 10 global crash reports per minute per application instance.

The backend is a second trust boundary because older/mixed-version clients can bypass browser-side protections. `ClientErrorDto` applies hard payload bounds and the analytics service repeats secret redaction, URL query/fragment removal, primitive-only metadata filtering, and stack-frame limits before persistence.

The endpoint remains public so bootstrap, authentication, and session-restoration failures can be observed. To limit abuse, NestJS applies an independent 30 requests/minute endpoint throttle. Do not add user IDs, access tokens, request bodies, chat text, Moment content, or arbitrary application state to this contract.

## Persistence and failure handling

Sanitised records are inserted into `client_errors` through the server-side Supabase client. A successful HTTP response means persistence succeeded. Supabase insert failures and provider exceptions return a stable `503` instead of falsely returning `logged`.

Backend warnings use fixed classifications (`client_error_persist_failed` and `client_error_persist_exception`) and deliberately omit raw provider error text. The browser treats any non-success response as best-effort telemetry failure and does not surface or recursively report it.

Existing retention/deletion policy for `client_errors` is unchanged by #1420. If retention is changed later, keep it bounded and document the operational requirement separately.

## Verification

Focused regression coverage verifies:

- Angular `ErrorHandler` registration and normal Error reporting;
- promise-style rejection unwrapping without arbitrary object inspection;
- credential/JWT redaction and URL privacy;
- bounded stack frames, duplicate suppression and burst limiting;
- safe `HttpErrorResponse` and unknown-throwable handling;
- reporting failure isolation;
- DTO size, frame-count, coordinate and timestamp validation;
- backend persistence sanitisation and primitive-only metadata;
- stable fail-closed behavior when Supabase rejects or throws.

Repository CI should additionally run the normal frontend/backend lint, typecheck/build and test suites.

## Rollout

This change is backward compatible with existing clients: the endpoint and persisted table remain the same. Deploy the backend first or together with the frontend. Older clients continue to post the same payload shape, subject to the new server-side validation, sanitisation and throttle.

Monitor the fixed persistence-failure warning classifications and endpoint 4xx/429/503 rates. A sudden rise in 400 responses indicates an older client is exceeding the documented bounds; a rise in 429 responses indicates a crash loop or abusive client.

## Rollback

No schema migration is required. Reverting the PR restores the prior handler/intake behavior. If only the frontend is rolled back, the hardened backend remains compatible with bounded legacy payloads. If only the backend is rolled back, the hardened frontend continues to send the existing endpoint shape.
